# Reelcast project map

Stack: Next.js 16, Supabase Auth + Postgres (Drizzle ORM), a Postgres job queue, Cloudinary storage, Pesapal billing. There is no Convex, Clerk or PayPal. See `README.md` and `docs/PROJECT-GUIDE.md` for the full picture.

- **Package manager:** bun only. `src/middleware.ts` keeps the name `middleware`; never rename it to `proxy`.
- **Browser → server** goes only through `POST /api/rpc`. Add a function in `src/server/modules/<domain>.ts` with `query`/`mutation`/`action` (`src/server/rpc/define.ts`); modules are listed in `src/server/rpc/registry.ts`. A module file may export only rpc definitions; put helpers in `src/server/lib/`. UI code uses `api`, `useQuery`, `useMutation`, `useAction` from `src/lib/rpc/client.ts`.
- **Always** scope data by `ctx.userId` and verify ownership of any id the client sends. Admin functions use `auth: "admin"`. Never return raw rows from `users`, `settings`, `youtube_channels`, `platform_settings` or `payment_*`; use the DTO builders (`src/server/lib/dto.ts`). Secrets are stored encrypted (`src/server/crypto.ts`).
- **Admin console:** `src/app/(admin)/admin/**` is a separate area with its own layout, sidebar and top bar (`src/components/admin/shell/`; the sidebar groups live in `nav-config.ts`). Wrap every admin page in `AdminPage`. The layout gates on the server and every admin function is `auth: "admin"`; the tests in `src/server/modules/admin/admin.test.ts` enforce that for the whole `api.admin` tree.
- **Collapsible sidebars:** the app and admin sidebars collapse to a 56px icon rail. The state is `data-sidebar-<app|admin>="collapsed"` on `<html>`, restored before first paint by the script in the root layout, and the layout follows it in CSS only via the `app-rail:` / `admin-rail:` variants (`globals.css`). A new nav item needs its label wrapped in a span with `app-rail:sr-only` (`admin-rail:sr-only` in admin) and a `title`; see `src/lib/sidebar-collapse.ts`.
- **Account data:** a user can edit their profile (`users.updateProfile`, pictures live in `reelcast/avatars/<userId>/` on Cloudinary) and delete their account (`users.deleteAccount`, `src/server/lib/accounts/deleteAccount.ts`). Deleting the `auth.users` row cascades through `users` to everything, so **every new table that holds user data must reference `users(id)` with `onDelete: "cascade"`**. Data keyed any other way (like `contact_submissions` by email) must be removed explicitly in `deleteAccount.ts`, and any new external file must be added to what it deletes first. `users.test.ts` fails when a table is neither cascaded nor handled.
- **Database:** edit `src/db/schema.ts`, run `bun run db:generate`, review the SQL in `drizzle/`, then `bun run db:migrate`. Every table must be RLS-locked with no API-role grants (see `drizzle/0001_security.sql`). Postgres is READ COMMITTED: make read-modify-write a single atomic statement; use `consumeQuota` (`src/server/lib/usage.ts`) for plan limits.
- **Background work** lives in `src/server/jobs/` (queue, `runTick`, one handler file per domain). Handlers must be idempotent, finish well under ~4 minutes, and resume long work with `deferMs`. Never call external APIs inside a DB transaction.
- **Tests and dev:** dev and prod may share one database: the dev ticker and `kickRunner` are off unless `DEV_TICK=1`, and DB tests may touch only rows they create (`inRolledBackTx`, or `createCommittedTestUser` for committed rows; queue calls take `scope: { userId }`). Never use a real account.
- **Tests:** `bun run test <file>` (bun test, scoped to `src/`, DB-backed with rolled-back transactions via `src/server/testing.ts`). Never run bare `bun test` (it would pick up `scratch/`). `bun run check` runs typecheck + lint.
- **Query cost:** every SQL statement is a network round trip to a remote database (about 0.4-0.8 s from a dev machine), so the NUMBER of statements is the performance budget. Never run a query inside a loop or `map(async ...)`; fetch with a join, `= any($1)` or one multi-row statement. Prefer one statement over several (scalar subqueries, `count(*) filter (where ...)`, a CTE) over `Promise.all`: production uses one connection, so concurrent queries are serialised. `db.execute(sql...)` returns timestamps as strings (use the builder when a result has timestamps). Prove it in a test: `countQueries(() => ...)` from `src/server/testing.ts` returns the statement count, so assert that it does not grow with N. The db client (`src/db/client.ts`) wraps postgres.js in `limitConcurrency` (`src/db/concurrency-limit.ts`): never remove it and never set `max_pipeline: 0` or `fetch_types: false` (pipelined statements hang through the Supabase pooler; `max_pipeline: 0` breaks transactions; `fetch_types: false` corrupts text arrays). `DATABASE_POOL_MAX` raises the pool size safely. See `docs/PERFORMANCE-AUDIT.md`.
